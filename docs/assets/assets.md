## What are assets ?

First of all, let's clearly define what are assets. Basically, they are anything used in a game that is persistent and not generated during runtime. For example, a texture is an asset, but a procedurally generated texture is not. A sound effect is an asset, but a sound effect generated by a synthesizer is not. A 3D model is an asset, but a 3D model generated by a procedural generation algorithm is not.
Technically even code is an asset, that generalization will come in handy later (if you find a way to reload it).

So when you have a game, when you start a new cutscene, you want the engine to be able to fetch the asset and play it. It seems simple putted that way, just take some chunk of video and splash it there, but no, as game are real time applications, time is angry player giving you 1/10 on Gamerant.com.

## Asset loading

So what is asset loading ? It's the process of fetching the asset from disk and putting it in memory. This seems simple and easy, but as hard disk aren't really speed freaks, they time some time to load assets.

Since hard drive read speed is constant, we can safely assume that if loading an asset of 100 Mb takes 0.2s, then 1Gb will take 2s.
So now the problem is that 0.2s is already huge, let's not talk about 2s.

It's tempting to say "Just use small assets", but except your game is a cosplay of Doom, then that's not really an option.

So here comes the 4 most used solutions:

- **Streaming**: Loading an asset per chunks that can be used as they are loaded. This a a common tricks for audio files, but can also be used for textures and 3D models. But it's also hard to determine whetever "streaming" means for a given asset of if it's even possible.

- **Asynchronous loading**: Loading an asset in a separate thread and using it when it's ready. This is a common solution for all kind of assets, but it requires a lot of efforts to implement, as while your thread takes his time to get the work done, your player is seeing thing that deserve a 1/10 on Gamerant.com. Plus it requires to be careful about temporal corehency as an asset that continue loading for a freed objects will cause a crash. May be easy to handle with loading abortion, reference counting, etc...

- **Preloading**: Loading an asset before it's needed. This is a common solution for all kind of assets, but it requires to know in advance what assets will be needed and when. This can be done by analyzing the game flow and preloading assets accordingly. But it can also be done by using a "loading screen" that will load assets in the background while the player is waiting. But this is not always possible, as some assets are only needed during gameplay and can't be preloaded. This also waste a lot of memory, as assets that may never be used are also loaded and that creates those painful loading screen, ask [Sonic 2006](https://sonic.fandom.com/f/p/4400000000000248372/r/4400000000001511942) about that.

- **Buying a SSD NVMe**: This is the upgrade of the regular HDD disk. It offers way better bandwith and can stream huge assets faster. But this require money, and some people (me) may not have the budget to buy a SSD NVMe. But it's also not always necessary, as some assets are small enough to be loaded quickly from a hard drive.

So we say the problem of loading assets. We may think "Ok, we saw the problem, we just have to be careful about assets size and loading time" but no.

## Assets Compressions

Now let's assume we eventually loaded the assets, you are tempted to use it but it's still in some ancient glyph.
It's still compressed.
In order not to make people download 100Gb of assets, game developers use compression to reduce the size of assets. A high compression ratio will reduce the size of the asset, allowing you so save some network bandwidth and disk space.

So what's the problem ? When you actually have to undo the compression. It's like getting into university, just pays some small fees to get in, take 5 years of your life to get out.

You paid to compress the assets, now decompressing it is way harder, done on CPU side and actually take a huge amount of time depending on how much was the compression ratio.

All assets are not compressed (sadly, all of those doesn't even need it) obvioulsy and differs in their algorithms. So it's a real bottleneck that we just can't avoid.

## Assets dependencies

As it would to easy it assets where just independent bundles data, they decided they should come with their friends and can't shine without them.
Those are for example meshes that may requires, materials, textures, animations, sounds, etc etc.

So it's often necessary to model those dependency.
Through a dependency graph... obviously.
A weighted dependency graph.

We can basically consider an asset like an fixed OS task, and weigh them (as we saw earlier, loading scale linearly with the asset size) by size and compression technics.

We can then apply some greedy work stealing scheduling to load all those asynchronously, in the correct order while still making the lightest appears as soon as possible instead of one big pop-up (like AI answering progressively instead of making the whole text and outputting it).

## Level of details

Level of details is a technique used to reduce the complexity of a 3D model as it gets further away from the camera. This is done by using different versions of the same model, each with a different level of detail. The engine will then choose the appropriate version of the model based on the distance from the camera. 
This can be generalized to this :

*Given an asset, following certain criteria, you can use a lighter version of it that is faster to load and use, but still looks good enough for the player.*

For sounds it's distance and priorities, for textures it's distance and screen size, for 3D models it's distance, whethever it's visible or not and screen size, for animations it's distance and priorities, etc etc.

This way we may imagine a hierarchical dependency graph for assets where in order to avoid default texture while the graph load, we can first load smaller versions, then progressively refine the texture as more details comes. One the most detailled texture is loaded, the other are freed.
